## The three instrumentation bugs (fixed)

1. **arr[0] cross-attribution** — both loops poll `/api/task/list` and take
   `arr[0]` (newest in the SHARED demo account), guarded only against their own
   anchor. Any task created by the other loop is silently adopted.
   Fix: capture the `POST /api/task` create-response uuid via a fetch wrapper
   (`window.__createdUuid`) and track by that uuid.
2. **engine_used read at the wrong instant** — a just-created neural task
   reports `engine_used=neural` before its pipeline resolves; the verdict
   fired on that transient instead of the task's final state.
   Fix: verdict from the tracked task's CARD: `user_state ∈ {DonePreview,done}`
   AND `engine_used=neural` AND `fallback_reason=null`.
3. **`exports_byte_verified` set unconditionally** — True even over two 402s.
   Fix: True only when the GLB carries the `glTF` magic AND both payloads
   are real (>1KB).

Applied to: `h3d_prod_neural_e2e.py` (CDP loop) and `h3d_neural_grind.py`
(raw loop) — same instrumentation pattern, plus `exports_ok` on the raw
grind's success record.

## Product bug discovered by the audit (fixed on production)

**A fallback task can wedge in `processing` forever** — task 88ab4d72-fd1e
stayed wedged 4.5h with ~500 card polls never reviving it.

Root cause chain:
- The fallback route called `enqueue()` bare (fire-and-forget) while the
  create route already wrapped its kick in `after()` — an oversight.
- The platform suspended the process mid-pipeline; the `finally` that would
  clear the in-memory `running` set never ran → that warm lambda instance
  was permanently "running" the task.
- `resumeStaleTask` early-returned on that same poisoned in-memory set, so
  every card poll served by the warm instance silently skipped recovery
  (resume_count never even incremented).
- Follow-up live verification showed the card route's `after()` callback
  never executes in practice on this deployment at all (7 polls against the
  fixed build still left resume_count null; all observed completions are
  explainable by lambda grace-period survival).

Fixes (hyper3d-clone, deployed + live-verified):
- `2ed18e6` — runPipelineNow (awaited, running-guarded); resumeStaleTask
  trusts the DB heartbeat, not the in-memory set; resume claims via a
  heartbeat+resume_count write; un-paced pipelines emit 2s heartbeats.
  Live evidence: fallback task 83028b0a's fast pipeline heartbeated `at`
  every ~2s and completed in 19s.
- `9ac18e8` — fallback route awaits the pipeline inline (deterministic,
  no after() dependence); card route fires the stale-resume pre-response.
  Live evidence: the wedged 88ab4d72-fd1e was revived via one fallback
  call (spec-resume path, ≤3s) → DonePreview/fast.
