ROOT CAUSE (definitive, smoking-gun evidence)
--------------------------------------------
The platform persists the project across reboots via an archive: at pre-stop the project
is captured to /home/sync/repo.tar; at boot /home/z/my-project is DELETED (except the
upload mount) and restored from that tar (start.sh lines ~60-98).

Proof from the live archive (captured 09:46, restored 10:08):
  tar tf /home/sync/repo.tar | grep db/
    → contains  db/custom.db                    (main project DB — GIT-TRACKED)
    → contains  ZERO entries under mini-services/hyper3d-clone-dev/db/
The mini-service's own .gitignore (line 9: "db/*.db") made its DB untracked+ignored →
excluded from the archive → wiped at every boot. The main project's .gitignore is narrow
(skills/ + node_modules/ only — start.sh "auto-heal" rewrites broader versions), so its
db/ directory IS carried.

DURABILITY RULE (empirical): a file survives reboots iff it is git-tracked (or in a
directory the archive demonstrably carries). Gitignored runtime state does not survive.

FIX (archive-proof, supersedes Task-34's path)
----------------------------------------------
1. Parity DB relocated to the main project's db/ folder under its own filename:
     /home/z/my-project/db/hyper3d-clone.db
   (distinct from custom.db — the main project's boot step `bun run db:push` targets
   custom.db via .env and would clobber a shared file's schema)
2. DATABASE_URL pin inside mini-services/hyper3d-clone-dev/package.json dev script
   updated to the new path (script-level env still beats platform env — Task-34 finding
   unchanged)
3. The DB file is GIT-ADDED (tracked) → guaranteed archive carriage. After any live
   change (seed, generations) re-stage: git add db/hyper3d-clone.db
4. Schema pushed with explicit CLI override:
     DATABASE_URL=file:/home/z/my-project/db/hyper3d-clone.db bun run db:push
