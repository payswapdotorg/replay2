## SECTION 2 — The parity DB incident (root cause + durable fix)

Symptom: sign-in on the parity instance returned HTTP 500 after the reboot.
Log: Prisma P2022 — "The column `main.User.username` does not exist in the current
database." The server's process env carried DATABASE_URL=file:/home/z/my-project/db/
custom.db — the MAIN project's database — inherited from the platform environment at
boot (process env overrides .env in Next.js). Task 32's fresh SQLite for the parity
instance had lived at a non-persistent path and was wiped by the reboot; the platform
boot then pointed the mini-service at the main DB, whose scaffold schema lacks the
parity schema's columns.

Durable fix (survives ANY launcher — platform boot or manual):
1. Persistent DB file: /home/z/my-project/mini-services/hyper3d-clone-dev/db/custom.db
   (schema pushed with DATABASE_URL explicitly overridden on the CLI — note: the
   Prisma CLI also lets process env override .env, so an explicit var is required
   for one-shot pushes).
2. DATABASE_URL pinned INSIDE the mini-service package.json dev script:
   "dev": "DATABASE_URL=file:/home/z/my-project/mini-services/hyper3d-clone-dev/db/
   custom.db next dev -p 3210 2>&1 | tee dev.log"
   (script-level env beats the inherited platform env for the server process;
   a .env file alone is NOT sufficient when the launcher exports DATABASE_URL)
3. The old main-project custom.db was left untouched (the accidental push attempt
   aborted safely: "not possible to execute this step" — 1 row preserved).
