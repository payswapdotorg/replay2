## 3. Task packet

**WFX-005 — Experience API shell.** This is the SOURCE-NEUTRAL use-case layer of
the Experience Core: TypeScript types + pure orchestration logic + fixtures ONLY.
No UI components, no provider connectors, no persistence — every external effect
is an injected PORT. Realization: `packages/experience/src/`.

Build these modules (file names may differ, this structure is required):

1. **`src/ports.ts` — the source-neutral seams (dependency inversion).**
   - `ConnectorPort` — the narrow slice of source access the Experience API needs:
     `search`, `metadata`, `resolve`, `executeAction`, optional `readLibrary` /
     `writeLibrary`. Structural type compatible with `SourceConnector` (a real
     connector is assignable to the port — prove it with a compile-time assertion
     like the pattern in `packages/domain/src/intent/infer.ts`).
   - `EventSink` — `emit(event: EntertainmentEvent): Promise<void> | void` — where
     watch-state events go (envelope/sessionId handled by caller or a wrapper).
   - `Clock` — `now(): number`. `IdGen` — `next(): string`. Both injected; no
     hidden globals, no `Date.now()` calls outside the injected clock.
   - A `Ports` bundle interface assembling all of them.

2. **`src/use-cases/feed.ts` — source-neutral feed.**
   - `getFeed(ports, ctx, request)` where request selects surface
     `'watch' | 'short'`.
   - Returns a typed `FeedPage`: ordered `FeedCard`s, each card combining an
     `EntertainmentItem` with its best available `SourceRealization` (capability
     information preserved — the Experience Core must know what each source can do).
   - Feed mode is chosen by CONTENT + SESSION CONTEXT (orientation/duration for
     short vs long-form), never by source.
   - Cards are assembled ONLY from connector port results — no direct provider
     types. Unsupported/empty search results produce an EMPTY page, never a fake
     card, never a thrown generic error.

3. **`src/use-cases/playback.ts` — playback session use-case.**
   - `startPlayback(ports, ctx, intent)` — resolve realizations for an item via
     the port, pick per the frozen precedence hint supplied by the resolver input
     (the full Native→Embed→Browser→External resolver is WFX-025 — here you only
     need to accept a chosen `PlaybackRealization` or a simple port-provided list),
     construct a `PlaybackSession` (frozen type) with resume position 0 or a
     supplied `resumePositionMs`, and emit a frozen `EntertainmentEvent`
     `type: "start"` through the EventSink.
   - `reportProgress`, `reportComplete`, `reportSkip` — progress mirroring:
     update a session's `resumePositionMs` (pure session map — an in-memory
     `PlaybackSessionStore` keyed by session id) and emit the matching frozen
     event types. All pure/typed; validation via the WFX-002 validators
     (`validateEntertainmentEvent`).

4. **`src/use-cases/library.ts` — library use-case.**
   - `getLibrary(ports, ctx)` — read through the optional port method. Connector
     without `libraryRead` capability ⇒ typed unsupported result
     (`{ ok: false; reason: "unsupported" }` style, mirroring the WFX-003
     `ConnectorResult` convention) — NEVER a thrown crash, NEVER an empty fake
     success.
   - `saveToLibrary` / `removeFromLibrary` — command through `writeLibrary` with
     the frozen `LibraryCommand` extension type; same unsupported semantics.

5. **`src/use-cases/actions.ts` — user action use-case.**
   - `runUserAction(ports, ctx, action: UserAction)` — through the port's
     `executeAction`; return the typed `ActionReceipt`; ALSO mirror the action as
     the matching frozen `EntertainmentEvent` (`like`/`save`/`share`/`follow`) via
     the EventSink when the connector confirms it.
   - Capability pre-check with a typed, actionable error when the connector lacks
     the capability for that action.

6. **`src/index.ts`** — public barrel: export every type + use-case + a
   `createExperienceApi(ports)` convenience facade bundling the use-cases.

7. **`src/fixtures.ts`** — deterministic fixtures: a fake `ConnectorPort`
   (in-memory items/realizations/library/actions), a recording `EventSink`, a
   fixed `Clock`/`IdGen`. NO randomness. These fixtures are how your tests (and
   later the lead's tests) drive the whole shell deterministically.
