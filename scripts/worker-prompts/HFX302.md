## 3. What you are building (the shape)

A provider-neutral adapter surface + two implementations + a corpus-driven
harness that, for EVERY corpus sequence, executes BOTH lanes against the
SAME deterministic baseline scene and compares the CANONICAL projections:

```
                     ┌─ reference lane: adapter(aise-engine-reference) ──→ the canonical
                     │        engine's applyOperation + quantity-models + validation
operation sequence ──┤                                                            │
(+ baseline scene,   └─ substitute lane: adapter(independent-reimplementation      │
   substitute profile)     or its coarse-grid twin) ──→ the INDEPENDENT            │
                          reimplementation (discretized accumulation +            │
                          independent validation re-check + independent topology)  ▼
                                                    project BOTH onto PROD-029's canonical points
                                                    (quantities ⊕ declared tolerance, validation
                                                     checks + verdict, topology constraints,
                                                     BOQ lines ⊕ declared tolerance)
                                                                  ▼
                       compatible | declared-incompatible(kind + tolerance breach)
                     | unsupported-by-substitute (the typed pre-execution gate)
```

The three behavior-matrix cells (closed vocabulary — `SubstitutionExpectation`):
- `compatible` — both lanes execute; the canonical projections are
  semantically compatible: every quantity within the substitute's declared
  per-dimension tolerance, validation verdicts AND per-check outcomes
  equal, topology constraints equal, BOQ lines within tolerance.
- `declared-incompatible` — both lanes execute; a projection diverges and
  the corpus entry DECLARES the expected comparison kind + the tolerance
  breach (e.g. the coarse-grid profile on a shape whose discretization
  error is designed to exceed the main tolerance — the divergence is the
  DESIGNED evidence that the comparison discriminates).
- `unsupported-by-substitute` — the sequence contains an operation family
  outside the substitute's declared capabilities: the adapter answers
  with the typed `unsupported` naming the family BEFORE execution; the
  record is the outcome (the reference lane may still execute — the
  engine governs both lanes equally).

NEGATIVE CONTROLS (mandatory — a benchmark that cannot fail is not a
benchmark):
- a TOLERANCE-BREACH mutation: perturb one projected quantity beyond the
  declared tolerance on the substitute side → the harness MUST report
  declared-incompatible with the quantity comparison kind (asserted with
  an intentionally-wrong twin fixture);
- a VERDICT mutation: flip one validation check outcome on the substitute
  side → MUST be caught with the validation comparison kind (the checks
  compare, not just the worst-of verdict);
- CAPABILITY HONESTY: a sequence containing an undeclared family → the
  typed `unsupported` (never computed), AND a sabotage twin — a provider
  descriptor over-declaring a capability the adapter cannot gate →
  rejected by `validateGeometryProviderDescriptor`;

  provider-specific field into a canonical projection → rejected (the
  D26 discipline asserted at this seam);
- the HISTORICAL REPLAY: with the substitute absent from the lane set,
  the committed records + goldens still parse, validate and re-project —
  a failed provider can be removed while historical solution records
  remain interpretable (the work order's final acceptance criterion).
