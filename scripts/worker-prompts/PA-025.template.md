## 3. The work

1. **The bounded tick composition**: extract a single-tick,
   bounded-batch entry from the workers host's seams (one claimDue batch
   through the delivery/outcome path + one processPending batch +
   optionally one reconciliation tick), composable from the environment
   the same way createWorkerHost is. The production host keeps its
   loop; the tick is the SAME logic bounded to one iteration.
2. **The authenticated endpoint**: an HTTP route (in the api service or
   a new worker-endpoint plane — your architectural call, narrated) that:
   - verifies the QStash delivery signature BEFORE anything else
     (QStashSignatureVerifier; fail-closed 401 on any verification
     failure — unsigned, wrong key, outside the replay window);
   - executes ONE bounded tick;
   - returns the tick's honest outcome summary (claimed/executed/
     delivered counts, remaining backlog) — observability only, never
     business state;
   - bounds its own runtime (a max-duration guard; a batch that would
     exceed it stops after the current item and reports partial
     completion — the next scheduled delivery continues).
3. **The QStash schedule wiring**: when configured (env: the QStash
   token + the receiver URL + the signing keys), a setup path publishes
   the recurring delivery (the provider's pinned publish API — add the
   minimal schedule surface if the port lacks it, narrated). The
   infrastructure wiring docs/env examples show the demo configuration
   (Upstash free tier: 1,000 messages/day — the schedule cadence must
   respect free-tier reality WITHOUT encoding it into correctness).
4. **The execution-facts battery**: end-to-end over the real seams —
   a command accepted through the API plane -> the tick endpoint invoked
   with a SIGNED delivery (the fake's signQStashDelivery) -> the command
   ADVANCES to executed (CAS write) -> the read model serves the
   projection (the EXECUTED-only law flips the honest empty state to the
   real resource) -> the outbox outcome commits. Plus the negative
   matrix: unsigned delivery 401; wrong-key 401; replay-window 401; the
   bounded-batch cap (a backlog larger than the cap advances exactly the
   cap, the remainder stays PENDING — honest partial progress); the
   idempotent re-delivery (the same delivery processed twice advances
   nothing twice — the dedupe/CAS proofs).
5. **The authorized e2e updates** (`tests/e2e/**`): the hosted e2e
   composition gains the tick endpoint (env-gated: when the endpoint is
   composed, the journey tests may drive it to advance commands — the
   Journeys 2/3/4 legs move from "activation stops on the honest
   not-found" to "the executed resource appears"; when NOT composed the
   existing honest-empty assertions stay). This update is authorized BY
   THIS PACKET — both directions must be pinned (composed -> advanced;
   uncomposed -> the current honest terrain).
6. **The closure note**: ONE dated additive note under the audit's §4
   Journeys 2/3/4: the execution path, its wiring contract, the battery
   evidence, and the honest "what the demo shows once configured".
