## Your work order (from WORK-REGISTRY.md §TL1-005, elaborated by the Lead)

Ensure a clear desktop shell and web-compatible shell story without
weakening capability boundaries. Acceptance: the parity posture of every
Flauz surface is classified, machine-checked, and documented; nothing
desktop-only silently breaks the web build; nothing web-shaped weakens a
desktop capability.

Deliverables:

1. `build/flauz/packaging-parity.json` — the parity registry: per Flauz
   extension (the six flauz-* extensions) and per product surface, a row:
   `{ surface, capability, class: "desktop-full" | "web-degraded" |
   "web-blocked" | "web-full", reason, evidence, recoveryPath }`.
   Evidence = the manifest key, engine constraint, or API proposal that
   forces the classification (e.g. `extensionEnabledApiProposals` entries,
   node-dependency declarations, browser field). Every row cites a file +
   key, never a guess.
2. `build/flauz/scripts/packaging-parity.mjs` — zero-dependency gate
   (node >= 20 stdlib only; never npm install): `--root <repo>` (default:
   repo containing the script), `--registry <file>` (default
   `build/flauz/packaging-parity.json`), `--json`, `--no-fail`,
   `--require`, `--help`. Modes:
   - default report: load the registry, re-derive each row's evidence from
     the live tree (manifest exists, cited key present, class consistent
     with the constraint), flag DRIFT rows (evidence moved/changed class
     without a registry update), and summarize per-extension posture;
   - exit 0 clean/SKIP (zero manifests found + no --require = documented
     SKIP), 1 drift/violation, 2 usage.
3. `docs/FLAUZ-PROGRAM/PACKAGING-PARITY.md` — the human report: the web vs
   desktop story in plain language (what a web build of Flauz includes,
   what it excludes, what degrades and why), the capability-boundary rules
   in force (which boundaries may NEVER be weakened — cite ARCHITECTURE-LOCK),
   and the recovery path per web-blocked surface (how it becomes web-capable
   later without forking core).
4. `build/flauz/packaging-parity.test.mjs` — node:test suite (>= 10 cases):
   registry-shape validation, evidence-derivation on fixtures, drift
   detection, SKIP semantics, usage errors, --help. Fixtures under
   `test/fixtures/packaging-parity/` (clean/, drifted/, empty/) modeled on
   the premium-ux-gate fixture family.
5. CI wiring: a `packaging-parity` job in `.github/workflows/flauz-hygiene.yml`
   (zero-dep, pre-install, report-only `--no-fail`, pinned action SHAs —
   copy the upstream-sync job's shape from TL1-001).
6. `build/flauz/scripts/verify-fixtures.sh` + README receipt-count updates,
   and the `.eslint-allowed-javascript-files` entries (same commit — the law).
