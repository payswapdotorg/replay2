## 3. The work

### 3.1 The provider profile schema (`packages/provider-registry/src/profile.ts`)

A machine-readable `ProviderProfile` covering EVERY mandatory field from the
layer-hardening work orders. Design notes:

- Zod-style runtime validation is NOT the house pattern — use TypeScript
  discriminated unions + pure validator functions with typed failure reasons
  (see `packages/solution-contract/src/` for the pattern).
- `license` must carry: the license identifier, a `commercialUse` boolean,
  an `intendedUse` declaration and a derived `evaluationOnly` flag (true when
  commercial use or intended use is not cleared).
- `failureModes` must use a CLOSED failure vocabulary (§3.4) — profiles
  cannot invent failure kinds.
- `benchmarkResults` are REFERENCES (benchmark record ids), never inlined
  scores.

### 3.2 The registry and promotion states (`packages/provider-registry/src/registry.ts`)

A pure, append-only registry: registration → state machine. States must
include at minimum: `registered`, `evaluation`, `benchmarked`, `promoted`,
`rejected`, `retired` — with LAWFUL transitions only (e.g. `promoted` requires
a benchmark record + a provenance manifest + a license clearing for the
intended use; `evaluationOnly` providers can never reach `promoted` for
production use). Transitions are events in an append-only log; the registry
derives current state deterministically. Re-registration of the same
providerId+technologyVersion is idempotent; a NEW technologyVersion is a NEW
registry entry (old one transitions to `retired` only explicitly).

### 3.3 Normalized I/O boundary (`packages/provider-registry/src/io.ts`)

The `ProviderInput`/`ProviderResult` normalized shapes: what a provider
execution may carry IN and OUT of the control plane. Provider-native formats
are captured as opaque provenance payloads, never parsed into canonical
domain types. Include a `normalizeResult` function that validates a raw
provider-shaped payload against the output contract declared in the profile
(typed failures, no throws).

### 3.4 Failure vocabulary (`packages/provider-registry/src/failures.ts`)

The closed vocabulary every profile and benchmark record must use. Include at
minimum: `perception-failure`, `retrieval-failure`, `reasoning-failure`,
`unsupported-data`, `operation-semantic-failure`, `resource-exhaustion`,
`timeout`, `license-blocked`, `contract-mismatch`. Each with a one-line
definition in the README. This vocabulary is the hook the layer-hardening
items (HFX-202/203/204's "benchmark suite can distinguish perception,
retrieval, reasoning, unsupported-data and operation-semantic failures") will
consume.

### 3.5 Benchmark result schema + provenance manifest
(`packages/provider-registry/src/benchmark.ts`, `provenance.ts`)

- `BenchmarkRecord`: providerId+technologyVersion, the benchmark id, metric
  values (comparable across providers of the same capability), failure
  observations (from the closed vocabulary), resource observations
  (compute/memory/latency profiles), and the deterministic reproduction
  statement (inputs digest + code version).
- `ProvenanceManifest`: the portable provenance chain — profile reference,
  input digests, normalized result digest, benchmark records, environment
  fingerprint (declared, not sensed), and the AISE-side consumer identity.
  Portable = the manifest is self-contained JSON, verifiable by digest.

### 3.6 The reference provider lifecycle (testkit + golden fixtures)
(`packages/provider-registry/src/testkit.ts`, `fixtures/`)

A deterministic REFERENCE provider (pure fixture, no network): a small
capability (e.g. "fixture-depth-estimation") with a fixed input contract, a
fixed output contract, two versions (one better, one license-blocked for
commercial use), and golden fixtures for: registration → execution →
normalized result → benchmark → provenance → promotion (v1), and the
license-blocked path (v2: registration → evaluation → benchmark →
license-gate REFUSES promotion). This lifecycle IS the exit gate.

### 3.7 Backend module (`backend/api/src/providers/**`)

Thin HTTP surface following the `solution-boq` module pattern: a route
factory (mounted by the Lead at the integration station) + service + model +
tests. Endpoints at minimum: profile registration/validation, registry state
query, benchmark record intake, provenance manifest retrieval, promotion
decision (with typed refusal reasons). All deterministic; no network egress.
