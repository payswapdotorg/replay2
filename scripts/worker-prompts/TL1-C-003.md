## Your work order (from WORK-REGISTRY.md §TL1-003, elaborated by the Lead)

Establish the smallest stable client-to-Flauz-service IPC/API seam for
commands, events, health, auth and lifecycle. Acceptance: a versioned
protocol usable by every feature TL without direct implementation coupling.

BACKWARD COMPATIBILITY IS HARD-BOUND: the existing extension code paths
(`extension.ts` calling `SeamClient.start` + the typed wrappers) and every
v0 wire shape (hello/ready, request/response envelopes, flauz.workspace.*
methods, shutdown) must keep working unchanged. The v1 protocol is
negotiated ADDITIVELY — a v0-only client against the new service and the
new client against a v0-only service both still work (state in the report
exactly how each direction is proven).

Deliverables:

1. `extensions/flauz-agent/core/protocol.mjs` — zero-dep Node, the versioned
   protocol definition, shared by service and conformance (extension source
   imports TYPES only, like contracts.d.mts does):
   - Protocol version ids (`'flauz.seam/v0'`, `'flauz.seam/v1'`) +
     negotiation rules: hello may carry `protocolVersions: string[]`;
     the service answers ready with the chosen `protocolVersion` and its
     capability list; a plain v0 hello (no field) negotiates v0.
   - Method namespace registry: `flauz.workspace.*` (existing, unchanged),
     `flauz.health.ping` / `flauz.health.status`,
     `flauz.lifecycle.initialize` / `flauz.lifecycle.shutdown` (graceful,
     idempotent), and the `flauz.auth.*` namespace SKELETON (v0: fail-closed
     — every auth method answers a structured not-implemented error; no
     token logic, no secrets — ARCHITECTURE-LOCK §3 security posture).
   - Error envelope: v1 errors are structured
     `{code, message, details?}` with machine-readable namespaced codes
     (`flauz.err.unsupported-version`, `flauz.err.unknown-method`,
     `flauz.err.invalid-params`, `flauz.err.internal`,
     `flauz.err.not-implemented`) — with a v0-compat rule (a v0 client
     still receives the string error shape).
   - Event envelope: server-initiated
     `{type: 'event', event, payload, ts}` formalizing the existing event
     relay, field-aligned with the FlauzEventEnvelope contract family
     (cite ARCHITECTURE-LOCK §5 in the module doc).
2. Adoption: `core/service.mjs` speaks the negotiated protocol (v1 when
   negotiated, v0 byte-compat otherwise); `src/seamClient.ts` sends the v1
   hello with v0 fallback, surfaces structured errors to callers without
   changing the existing method signatures, and adds thin typed wrappers for
   health/lifecycle only (auth stays skeleton). Keep TS changes minimal and
   consistent with existing types; the existing test suite is the compat
   proof.
3. Conformance: `extensions/flauz-agent/test/protocol.conformance.test.ts`
   (node --test, spawning the REAL service via child_process — the
   seamClient.test.ts pattern) asserting: v0 handshake byte-compat; v1
   negotiation both directions; version-mismatch rejection with the
   structured error; unknown-method + invalid-params error codes; health
   ping/status; lifecycle shutdown idempotence; event envelope shape on a
   real relayed event; malformed-line tolerance. Every rule has a case that
   proves it fires.
4. `docs/FLAUZ-PROGRAM/SERVICE-SEAM.md` — the cross-TL seam document: the
   wire protocol spec (v0 + v1), the versioning policy (additive, negotiated,
   deprecation ladder — a version is deprecated by announcement + one cycle,
   never by breakage), the method-namespace registry table, the error-code
   table, the event catalog, and the migration guide for feature TLs
   (TL2/TL3 adopt namespaces, never implementation internals).
5. `.eslint-allowed-javascript-files`: add the line for
   `extensions/flauz-agent/core/protocol.mjs` IN THE SAME COMMIT (precedent:
